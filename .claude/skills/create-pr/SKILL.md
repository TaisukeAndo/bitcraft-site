# bitcraft-site の PR 作成

## なぜこの手順が必要か

このリポジトリ（bitcraft-site）は GitHub Pages で配信されている静的サイトで、`main` ブランチへの変更がそのまま本番公開に直結する。ビルドやテストの仕組みは無いため、コードの誤りを機械的に検知する手段がない。そのため「作業ブランチ → PR → レビュー」という一手間が、本番事故を防ぐ実質的なセーフティネットになる。`main` に直接コミットして push することは避け、常にこのスキルの手順を踏むこと。

## 手順

### 1. 現状を把握する

```bash
git status
git branch --show-current
git diff
git diff --staged
```

- 変更が何もなければ、その旨をユーザーに伝えて終了する。
- ステージされていないファイルがある場合、それが今回のPRに含めるべき変更かを diff の内容から判断する。無関係な一時ファイルや `.DS_Store` のようなゴミが混ざっていないか確認する。
- 万一 `.env` や認証情報らしきファイルが変更/追加されている場合は、内容を確認してから扱う。含めるべきでないものは `git add` の対象から外す。

### 2. ブランチを決める

- **現在 `main` にいる場合**: 変更内容から短い英語の kebab-case ブランチ名を考えて新規作成する（例: `add-speaker-section`, `fix-seminar-seats-count`）。このリポジトリの既存ブランチ（`add-ai-agent` など）も同じ命名スタイルなので揃える。
  ```bash
  git checkout -b <branch-name>
  ```
- **既に `main` 以外のブランチにいる場合**（例えば作業中に既にブランチを切っていた、またはステージ済みの変更が既にそのブランチ上にある場合）: 新しくブランチを切り直す必要はない。そのまま今のブランチを使う。

### 3. コミットする

このリポジトリのコミットメッセージは日本語の体言止め・簡潔な要約1行＋箇条書きの詳細、というスタイル（`git log` で確認できる）。これに合わせる。

```bash
git add <対象ファイル>
git commit -m "$(cat <<'EOF'
<変更内容を要約した日本語の見出し>

- <変更点1>
- <変更点2>

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
```

見出しは「〜を追加」「〜を更新」「〜を修正」のように、実際の変更の意図（何を・なぜ）が伝わる一文にする。ファイル名の羅列で終わらせない。

### 4. push する

```bash
git push -u origin <branch-name>
```

### 5. PR を作成する

`gh pr create` で日本語のタイトル・本文を付けて作成する。本文は以下のテンプレートに沿う。テストコマンドが存在しないサイトなので「Test plan」ではなく、実際に目視確認すべきページ・箇所を書く。

```bash
gh pr create --title "<コミット見出しと同様の簡潔な日本語タイトル>" --body "$(cat <<'EOF'
## 概要
- <変更点を1〜3個の箇条書きで>

## 確認方法
- <該当ページのパスなど、ローカルやプレビューで見るべき箇所>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

作成後、`gh pr create` が返す PR の URL をユーザーに提示する。追加の確認は挟まず、状況把握からPR作成までを一気に実行してよい（ユーザーが明示的にこのフローを了承済み）。ただし2で述べた「機密情報が混ざっていないか」の確認だけは省略しない。

### 6. 既存PRがある場合

同じブランチに対して既にPRが開いている可能性があるので、`gh pr create` の前に以下で確認してもよい。既にあれば新規作成せず、そのPRのURLをそのまま案内する。

```bash
gh pr view --json url 2>/dev/null
```
