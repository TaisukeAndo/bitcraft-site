# 問い合わせ・申込みフォームの追加とGAS自動返信

## なぜこのSkillが必要か

`contact/` や `service/seminar/*/apply/` は、見た目はサイト内のフォームだが実体は `fetch(..., { mode: "no-cors" })` でGoogleフォームの `formResponse` エンドポイントへ直接POSTするという、素朴だが実績のあるパターンで統一されている（詳細は `CLAUDE.md` とAskUserQuestionで確認済みの通り、独自バックエンドを持たない静的サイトゆえの設計）。ただし今のところ、送信後にユーザーへ何か自動で連絡が届く仕組みは無い。`no-cors` で送っている以上サイト側のJSは送信の成否すら読めないため、「本当に届いたか」「次に何をすればいいか」を伝える手段が確認メール以外に無いのに、その確認メールを送る仕組みが存在しなかった、というのがこのSkillが埋めるギャップ。

## 全体像：2つの独立した仕組みの組み合わせ

フォーム1つに対して、性質の異なる2つの仕組みが組み合わさっていると理解する。この2つは疎結合であることが重要:

1. **サイト側フォーム → Googleフォームへの直接POST**（既存パターン踏襲）
   各 `<input>`/`<textarea>` の `name` 属性にGoogleフォーム側の質問ID（`entry.xxxxxxxxx`）を対応させ、`apply-script.js` 相当のJSが `no-cors` でPOSTする。entry IDの調べ方・当てはめ方は `add-seminar` Skillの `references/google-form-fields.md`（`../add-seminar/references/google-form-fields.md`）を参照する。このSkill独自の説明は増やさず、既存のものを再利用する。

2. **Googleフォームの回答 → 連携スプレッドシート → GASの `onFormSubmit` トリガー → 自動返信メール**（このSkillで新規に追加する部分）
   GASスクリプトは `entry.xxxxxxxxx` を一切見ない。フォーム回答が書き込まれたスプレッドシートの**列見出し＝Googleフォームの質問タイトル文字列**をキーに回答を拾う（`e.namedValues["メールアドレス"]` のような形）。

**この2つが疎結合であることの実務上のメリット**: entry IDはGoogleフォームを実際に作成した瞬間に確定する値なので、`add-seminar` のパターンB（フォーム未作成でプレースホルダーのまま進めるケース）のように、まだGoogleフォームが無い段階でもGASスクリプトだけは先に完成させられる。後でGoogleフォームを作る際に「質問タイトルの文言をHTML側の入力ラベルと一字一句揃える」ことさえ守れば、GAS側のコードは一切書き直さずに済む。逆に言えば、質問タイトルの表記ゆれ（全角/半角、末尾の「？」の有無など）はGASが回答を拾えなくなる唯一にして最大の原因なので、ここだけは強調してユーザーに伝える。

## ステップ0: 情報収集

以下が揃っているか確認する。ユーザーが最初のメッセージで既に書いている項目は聞き直さない。

**フォームページ自体について:**
- 用途（問い合わせ／申込み）、対象のサービス・セミナー名、キャッチコピー
- 設置場所（新規ディレクトリか、`add-seminar` で既に足場が作られた `apply/` を使うか）
- フォーム項目（お名前・メールアドレス以外に何が要るか）
- Googleフォームが作成済みか（済みなら送信先URLと各項目の`entry.xxxxxxxxx`、未作成なら `google-form-fields.md` のパターンBに従う）

**GAS自動返信について（このSkイルの核心）:**
- 返信メールの件名・本文・差出人表示名・CC/BCC
- 返信に使うデータ（宛先メールアドレスの質問タイトル、本文に差し込みたい項目があればその質問タイトルも）
- 振込先や注意事項など、本文に定型で入れたい情報。**銀行口座番号のような実在の機微情報は絶対に推測・でっち上げない**。ユーザーから明示された値だけを使い、無ければ `【振込先情報をここに記載】` のような明確なプレースホルダーにする
- 詳細ページなど他のページに矛盾する記載（例:「当日現地でお支払い」なのに事前振込を案内する等）がないか確認し、あれば気づいた時点でユーザーに整合性を取ってよいか確認する（黙って両方残さない）

## ステップ1: サイト側フォームページを用意する

- ゼロから作る場合は `contact/`（問い合わせ向け）または既存の `service/seminar/*/apply/`（申込み向け）を土台にコピーし、見出し・項目・パスの深さを新しい設置場所に合わせて調整する。ヘッダー/フッターの複製・スクリプト読み込み順序は `CLAUDE.md` に書かれた全ページ共通の型を踏襲する。
- `add-seminar` が既に足場を作ってあるページ（`GOOGLE_FORM_URL` が `TODO` のままの `apply-script.js`）に対して行う場合は、そのページ構造をそのまま使い、entry ID周りの扱いは `google-form-fields.md` のパターンA/Bに従う。
- サンクスメッセージ（`#thanks-message` 相当）の文言は、後述のGAS自動返信が実際に送られることを踏まえて「数日以内に確認メールを送ります」のような曖昧な表現ではなく、「この後すぐ確認メールが届きます。数分経っても届かない場合は迷惑メールフォルダをご確認ください」のように自動送信であることが伝わる書き方にする。

## ステップ2: GAS自動返信スクリプトを作る

`assets/Code.gs.template` を土台に、そのフォーム専用の `Code.gs` を作る。ファイル冒頭の `CONFIG` オブジェクト（宛先メールアドレスの質問タイトル・件名・CC・差出人名）と、本文を組み立てる `buildBody()` をステップ0で集めた内容で書き換える。生成した `.gs` ファイルは、そのフォームが属するフォルダ配下に `gas/Code.gs` として置く（例: `service/seminar/<slug>/gas/Code.gs`）。GASはブラウザ経由のApps Scriptエディタに手動で貼り付けて使うものなので、このリポジトリ内のファイルはあくまで**ソースの控え・レビュー用**であり、それ自体が自動デプロイされるわけではないことをユーザーに明言する。

スクリプトの詳しい設計方針（`onFormSubmit` の受け取り方、`MailApp` の送信オプション、送信元アドレスの制約、送信クォータなど）は `references/gas-setup.md` を参照。

## ステップ3: 手動セットアップ手順をユーザーに提示する

Claude Codeはブラウザ操作・Googleへのログイン・Apps Scriptの認可フローを代行できない。そのためこのSkillの成果物は「コード＋手順書」までで、以下はユーザー自身の作業になることを最初に明言する:

1. Googleフォームを作成し、質問タイトルをHTML側の入力ラベルと**完全一致**させる
2. フォームの「回答」タブから連携スプレッドシートを新規作成する
3. スプレッドシートの「拡張機能」→「Apps Script」を開き、`Code.gs` の中身をこのSkillが生成したコードに置き換える
4. トリガー（時計アイコン）で `onFormSubmit` を「スプレッドシートから」「フォーム送信時」で追加し、保存時の権限承認を許可する
5. 事前入力リンク機能で各質問の `entry.xxxxxxxxx` を確認し、サイト側フォームの `GOOGLE_FORM_URL` と `name` 属性を実際の値に置き換える（ステップ1で保留していた場合）
6. テスト送信して自動返信メールが実際に届くか確認する

詳細な画面操作は `references/gas-setup.md` に手順として書いてあるので、要約せずそのまま案内してよい。

## ステップ4: 最終チェック

- サイト側フォームの各入力ラベル文言と、GASの `CONFIG` が参照する質問タイトル文字列が一字一句一致しているか突き合わせる（表記ゆれが唯一にして最大の失敗要因なので、コピペで済ませずに1つずつ確認する）
- 本文中に実在しない・未確認の情報（振込先、電話番号、日程など）を埋めていないか確認する
- 他のページ（詳細ページのOVERVIEW等）とメール本文の記載内容（支払い方法・金額・期限）が矛盾していないか確認する
- ユーザーへの最終報告で、(a) 今回作成・編集したファイル一覧、(b) Googleフォーム未接続なら明言、(c) ステップ3の手動セットアップがまだ完了していないことを明示する

このリポジトリで変更をコミット・PR化する流れは `create-pr` Skillが別途あるので、ユーザーがそれを望んだらそちらに任せる（このSkillの範囲はファイルの作成・編集と手順書の提示まで）。
