# Googleフォーム質問仕様書（コピペ用）

`apply/index.html` の申込フォームに対応する、実際に作成すべきGoogleフォームの質問一覧。上から順にGoogleフォームの編集画面へそのまま入力していけば完成する。

**重要: 質問タイトルは一字一句このとおりに入力すること。** 特に「お名前」「メールアドレス」の2つは `gas/Code.gs` の `CONFIG.NAME_FIELD` / `CONFIG.EMAIL_FIELD` が文字列一致で参照しており、全角/半角・句読点・表記が1文字でもずれると自動返信メールが静かに送信されなくなる（エラーにもならないため気づきにくい）。

作成後にやること: 各質問の「⋮」→「事前入力したリンクを取得」で `entry.xxxxxxxxx` を確認し、`apply/index.html` の対応する `name` 属性と `apply/apply-script.js` の `GOOGLE_FORM_URL` に反映する。

**→ 対応済み。** 実際のGoogleフォーム（<https://docs.google.com/forms/d/e/1FAIpQLScDbru2yfQwWov5n5heSOexj0-xeDSZMldRmxB8Dw7Mh9poHw/viewform>）のentry IDを `apply/index.html` と `apply/apply-script.js` に反映済み。ただし「お名前」の質問タイトルが `gas/Code.gs` の `CONFIG.NAME_FIELD`（"お名前"）と一字一句一致しているかは、Googleフォームの編集画面で目視確認すること（本仕様書どおりに作成されていれば問題ないはずだが、GAS設置前に必ず確認する）。

**「その他」を選択できる質問（5・7・9）について:** Googleフォームの選択肢一覧に手入力で「その他」を追加するのではなく、ラジオボタン/チェックボックス質問の編集画面下部にある **「'その他' を追加」** トグルをONのまま使う。これにより「その他」を選んだ回答者に自由記述欄が自動的に表示される。実際の送信データは2つのentry IDに分かれる:
- 選択肢そのものの `entry.xxxxxxxxx`（「その他」を選ぶと値は `__other_option__` になる）
- 自由記述欄の値が入る `entry.xxxxxxxxx.other_option_response`（末尾に `.other_option_response` が付いた別ID、entry番号自体は選択肢と同じ）

サイト側（`apply/index.html`）は既にこの2つを前提にマークアップ済み。**Googleフォーム側の設定変更は不要**（下記「検証結果」参照）。当初、ブラウザからの実送信で `400 Bad Request` が発生したため一時的に「トグルOFF＋JS側で選択肢の値を書き換える」方式に変更していたが、`curl` で `formResponse` エンドポイントに直接POSTして原因を切り分けたところ、`entry.xxxxxxxxx=__other_option__` ＋ `entry.xxxxxxxxx.other_option_response=<自由記述>` の組み合わせ自体は `fbzx` やセッション由来のトークン（`dlut`／`partialResponse`／`_sentinel` 等、Googleの本物のフォームページを開いたときだけ動的に発行される内部トークン）が無くても正常に受理されることを確認した（urlencoded・multipart/form-data の両方、`_sentinel` の有無に関わらず一貫して200・「回答を記録しました。」）。そのため当初の400は「'その他' を追加」機能そのものの制約ではなく、別の一時的な要因だったと判断し、ネイティブの「その他」機能を使う元の方式に戻した。

## 経緯: 一時400エラー → curlでの検証 → ネイティブ「その他」機能を採用

**発生した事象:** 「ご職業・ご所属」「現在利用しているAIツール」「社内で自動化・効率化したい業務領域」のいずれかで、Googleフォーム標準の「その他」を選び自由記述を入力してブラウザから実送信すると、一時的に `POST .../formResponse` が `400 Bad Request` になる不具合が確認された。

**切り分け:** `curl` で `formResponse` エンドポイントに直接POSTし、以下の組み合わせを比較した:
- 通常の選択肢のみ（Other無し） → 200 OK
- `entry.xxxxxxxxx=__other_option__` ＋ `entry.xxxxxxxxx.other_option_response=<text>`、`_sentinel`等の付随フィールド無し → 200 OK
- 上記に `entry.xxxxxxxxx_sentinel=`（空値）を追加 → 200 OK
- ページ内の全選択式質問分の `_sentinel` を追加 → 200 OK
- `multipart/form-data`（ブラウザの `FormData` と同じエンコーディング）で送信 → 200 OK

いずれも `entry.xxxxxxxxx.other_option_response` の内容を含めて正常に「回答を記録しました。」が返り、`fbzx`／`dlut`／`partialResponse`／`_sentinel` のようなGoogleの本物のフォームページを開いたときにだけ動的発行される内部トークンが無くても、ネイティブの「その他」機能（`__other_option__` 方式）はこのフォームに対して問題なく機能することを確認した。

**結論:** 当初の400は「'その他' を追加」機能そのものの構造的な制約ではなく、別の一時的な要因（当時のGoogleフォーム側の設定変更が反映しきっていなかった等）だった可能性が高い。そのため実装は当初どおりネイティブの「その他」機能（Googleフォーム側は「'その他' を追加」トグルON、サイト側は `entry.xxxxxxxxx=__other_option__` ＋ `entry.xxxxxxxxx.other_option_response`）に戻した。Googleフォーム側の設定を変更する必要は無い。
